PB authority model: Promptbranch is the deterministic control plane and release authority. ChatGPT is the reasoning and execution surface. Human-readable assistant prose is advisory; validated JSON, tests, ZIP checks, current-state reads, backend-first reads, transactional writes, and adopted artifact evidence are operational.

The whole PB system in one model

Promptbranch, shortened here as PB, is a local workflow shell around ChatGPT Projects. Its purpose is to make ChatGPT-assisted development reproducible, stateful, and release-controlled.

flowchart LR
  Operator[Operator] --> PB[pb CLI / local host]
  PB --> State[Workspace / Task / Artifact state]
  PB --> Repo[Local repo: VERSION, docs, tests, ZIPs]
  PB --> ChatGPT[ChatGPT Project + conversation]
  PB --> MCP[MCP server: deterministic tools]
  PB --> Validators[Schema, docs, ZIP, test validators]
  ChatGPT --> Reply[Advisory prose + structured JSON reply]
  Reply --> PB
  Validators --> Evidence[Operational evidence]
  Evidence --> Registry[Artifact registry / accepted baseline]
  Registry --> PB

State model: workspace, task, artifact

PB avoids treating ChatGPT.com like a filesystem. Instead, it uses explicit state scopes and updates them independently.

{
  "workspace": {
    "project_home_url": "...",
    "project_name": "...",
    "project_slug": "..."
  },
  "task": {
    "conversation_url": "...",
    "conversation_id": "...",
    "title": "..."
  },
  "artifact": {
    "artifact_ref": "...zip",
    "artifact_version": "v...",
    "source_ref": "...zip",
    "source_version": "v..."
  }
}

The important rule is that selecting a task must not accidentally mutate workspace state, and installing a development candidate must not automatically turn it into the accepted baseline.

Ask/reply protocol and artifact intake

The ask/reply protocol converts a ChatGPT conversation into a controlled transaction. The assistant may explain, but PB only automates from a validated reply envelope.

  1. Request: pb ask --protocol builds a structured request with workspace, task, baseline, target version, constraints, and expected reply schema.
  2. Reply: ChatGPT returns advisory prose plus one structured reply envelope.
  3. Parse: PB extracts exactly one protocol block and validates schema, IDs, baseline, and artifact metadata.
  4. Candidate: artifacts become candidates, not accepted baselines.
  5. Verify: ZIPs must pass version, layout, hygiene, and continuity checks.
  6. Adopt: adoption happens only after the configured validation path is green and PB verifies current state.
sequenceDiagram
  participant O as Operator
  participant PB as pb
  participant C as ChatGPT
  participant R as Repo/Registry
  O->>PB: pb ask --protocol
  PB->>C: structured request + constraints
  C-->>PB: prose + promptbranch.ask.reply JSON
  PB->>PB: parse + schema/baseline validation
  PB->>R: register verified candidate only after ZIP checks
  O->>PB: explicit install/test/adopt action
  PB->>R: update accepted baseline only after verification

Agent, MCP, and skills

PB is designed to become its own local host/client for deterministic tools. MCP provides capabilities. Skills provide procedures. Ollama may propose or summarize, but it does not execute or own state.

Allowed early

  • Read-only MCP tools.
  • Repo inspection.
  • Git status / diff summary.
  • Skill-guided read-only planning.
  • Controlled smoke tests.

Blocked until proven

  • Autonomous source overwrite.
  • Write-capable MCP from model proposal.
  • Broad shell execution.
  • Remote skill downloads.
  • Artifact release/adoption without deterministic gates.
pb agent run "read VERSION and git status" --path . --json
pb skill list --json
pb skill validate .promptbranch/skills/repo-inspection --json
pb agent run --skill repo-inspection "inspect repo" --path . --json

Release lifecycle

PB treats a release as more than a generated ZIP. A complete release lifecycle includes candidate install, Project Source visibility, validation, adoption, current-state verification, policy sync, and Git hygiene.

stateDiagram-v2
  [*] --> CandidateBuilt
  CandidateBuilt --> Installed: install ZIP
  Installed --> SourceVisible: add/verify Project Source
  SourceVisible --> Tested: run configured checks
  Tested --> Adopted: green + adopt
  Adopted --> CurrentVerified: pb artifact current / baseline-status
  CurrentVerified --> PolicySynced: update policy for next release
  PolicySynced --> GitClean: commit/push expected files
  Tested --> Blocked: failed validation
  SourceVisible --> Blocked: source not verified
  Installed --> Blocked: ZIP/layout/version defect

Operational invariants

Backend-first reads

Read structured backend/network payloads before DOM scraping. DOM is fallback; OCR is last resort.

Transactional writes

Trigger, wait for settled state, re-read, verify persistence, then update PB state.

Candidate before accepted

Generated or downloaded artifacts are candidates until PB verifies and adopts them.

JSON is operational

Validated JSON, ZIP checks, tests, and registry/current-state reads drive automation.

Prose is advisory

Assistant text can explain or propose but cannot approve releases or mutate state.

No silent mutation

Source sync, adoption, Project Source add, and Git synchronization require explicit verifiable actions.
